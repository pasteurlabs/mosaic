Mosaic:A Benchmark Suite for Differentiable Physics Solvers

Andrin Rehmann, Heiko Zimmermann, and Dion Häfner, Pasteur LabsNeurIPS 2026, Evaluations and Datasets track

What does it take to get usable gradients out of a differentiable PDE solver? Practitioners usually find out by trial and error. Mosaic puts 14 solvers behind one forward and gradient interface, whatever their language or way of computing gradients, and measures their accuracy, gradients, cost, and integration effort on shared tasks, so that you can compare them before committing to one.

import jax
import jax.numpy as jnp
from tesseract_core import Tesseract
from tesseract_jax import apply_tesseract
from mosaic_shared.problems.navier_stokes_grid.schemas import make_vortex_ic

v0 = make_vortex_ic(N=64, seed=42)
image = "exponax_navier_stokes_grid:latest"

with Tesseract.from_image(image) as solver:
    def loss(v0):
        inputs = {"v0": v0, "viscosity": jnp.array([0.01]), "steps": 50}
        return jnp.mean(apply_tesseract(solver, inputs)["result"] ** 2)

    grad_v0 = jax.grad(loss)(v0)

Exponax is a spectral solver written in JAX and differentiated with reverse-mode AD.

What we found

On every task, the solvers that return gradients agree with finite differences and reach comparable optima. They differ in how much work they take to integrate, what their gradients cost, and whether they have the features, stability, and memory a task needs.

These findings describe the solvers as pinned for the paper, at the tag v0.3+paper-repro. The current results track the latest solver versions and may differ.

Integration effort varies widely

Even among solvers built on AD frameworks, the gradient code needed to wrap them ranges from 20 lines or fewer to more than 200. Some defects only surface in the checks, and the solver reference records each fix with its reason.

When results match, cost decides

Where all solvers reach equivalent results, as on the steady heat and structures tasks, speed and integration effort decide the choice.

Feature completeness, stability, and memory are the real bottlenecks

Some solvers lack features a task needs, such as boundaries that are not periodic. On long rollouts, all of them eventually run out of GPU memory, and some return non-finite gradients well before that.

Many differences only show up in a benchmark

Solvers that share a framework, a discretization, and a time stepper still differ in stability, and nothing in their design or gradients predicts which ones fail. Testing candidates on the task at hand is what Mosaic is built for.

Tasks and solvers

Each task is an optimization problem without learned components, so the solver's gradient is the only thing under test. Every solver that supports a task's physics runs it through the same interface, and forward-only solvers serve as references.

Heat transfer

Recover a conductivity field from temperatures.

FEniCS, Firedrake, JAX-FEM, torch-fem, and deal.II (forward only)

Structures

Make a cantilever as stiff as possible with a fixed amount of material.

FEniCS, Firedrake, JAX-FEM, TopOpt.jl, torch-fem, and deal.II (forward only)

2D flow

Shape the inflow to lower the drag on a cylinder, and check gradients on periodic flows.

Exponax, INS.jl, JAX-CFD, PhiFlow, PICT, Warp-NS, XLB, and OpenFOAM (forward only)

3D flow

Recover an initial velocity field from a later snapshot.

The same eight fluid solvers as in 2D, with OpenFOAM (forward only) as the reference.

How Mosaic works

Mosaic runs every solver through the same forward and gradient calls and never looks inside it, so the same checks apply to all of them.

Forward accuracy

Reference agreement. Error against analytic solutions, literature values or converged high-resolution runs, within a tolerance.

Convergence. How the error shrinks as the resolution increases.

Gradient quality

Gradient accuracy. Agreement with finite differences over a range of step sizes, with exact gradients where they exist, and through chains of calls.

Optimization. Convergence with the same optimizer and budget for every solver on a task.

Compute cost

Scaling. Wall time and peak memory of the forward and gradient calls across problem sizes.

Rollout length. How long a rollout one gradient call handles before the solver runs out of memory or time.

Development cost

Setup compatibility. Whether the solver can express the task, and why not if it cannot.

Integration effort. Every departure from a solver's default usage, with its reason and evidence, rated from L0 (a documented option) to L3 (a change to the solver itself).

Run a solver yourself

Every solver in Mosaic is a Tesseract, a container that exposes a forward pass and a vector–Jacobian product whatever the solver's language. The code at the top of this page runs as it is once you have installed the shared schemas and a differentiation bridge, and built the solver's image:

$ git clone https://github.com/pasteurlabs/mosaic && cd mosaic
$ pip install -e mosaic/mosaic_shared tesseract-jax   # or tesseract-torch; needs Python 3.12+
$ tesseract build mosaic/tesseracts/navier-stokes-grid/exponax

The standalone guide covers PyTorch, the mesh solvers, GPUs, and loading a solver without a container.
