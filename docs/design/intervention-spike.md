# Intervention annotations: spike findings

**Status:** spike on branch `spike/intervention-annotations` (not for merge). The
decisions taken from it are in [interventions.md](interventions.md).

All 19 tesseracts on `main` were annotated following the first draft of
[interventions.md](interventions.md): an `interventions:` list in each
`tesseract_config.yaml`, and `mosaic-intervention` marker comments around the
implementing code. The annotations change no behavior; the source diffs are
comments and blank lines only. The aggregated data is in
[intervention-report.md](intervention-report.md), generated by
`python docs/design/intervention_report.py --out docs/design/intervention-report.md`.

The question was whether the ladder (L0 documented use, L1 undocumented
configuration, L2 user code on public primitives, L3 changing the solver)
makes sense in practice. Short answer: L3 and the requirement to state a "why"
work well. The level alone does not carry enough information, and several
things practitioners care about most fall outside the ladder.

## Numbers

|                             |                                                                                                                             |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Records                     | 92 across 19 tesseracts                                                                                                     |
| By level                    | L0 39, L1 22, L2 23, L3 8                                                                                                   |
| Confidence of the "why"     | verified 8, stated 50, inferred 34                                                                                          |
| Most common consequence     | `too-slow` (27), then `inaccurate-forward` (17), `crash` (14)                                                               |
| Highest level per tesseract | L3: PhiFlow, PICT, XLB, FEniCS (both), TopOpt.jl. L2: Exponax, INS.jl, jax-cfd, Warp-NS, Firedrake heat. L1 or L0: the rest |

Only 8 of 92 "why"s are backed by something reproducible. Most of the rest
rest on a single code comment or PR description by the person who wrote the
code. Many "inferred" records say "none found": for example, every OpenFOAM
channel setting introduced in #239, and the linear solver choices of deal.II
and JAX-FEM.

## What works

**L3 is crisp.** The eight L3 cases each have a clear story: PhiFlow's int64
monkeypatch of `NumPyBackend` (upstream tum-pbs/PhiML#16 still open), the
FEniCS adjoint `linalg_solve` monkeypatch (both tesseracts), PICT's
warm-started pressure solves through private `PISOtorch_diff` calls and its
`sed -i` build patch, XLB's build-time edit of its own source and its smooth
KBC stabiliser, and TopOpt.jl's `Core.eval` patch of the INP parser.

**The lint is promising.** The heuristic lint in `intervention_report.py` hit
7 lines in the current code, all inside annotated L3 regions, with no false
positives. It caught 5 of the 8 L3 records. Caveat: the annotating reviewers
knew the lint rules, which may have pulled classifications towards what the
lint detects. The three misses need different rules:

- writes into site-packages from a build step (XLB);
- subclassing a library class to replace its algorithm through a public
  extension point (XLB's smooth KBC; PICT's `Simulation.linear_solve`
  override);
- `Core.eval` into a foreign Julia module (TopOpt.jl).

**Cross-library contrasts are informative.** The same need lands at very
different levels:

| Need                       | Library A                                 | Library B                                     |
| -------------------------- | ----------------------------------------- | --------------------------------------------- |
| MUMPS in the adjoint solve | FEniCS: L0 setting plus an L3 monkeypatch | Firedrake: default, nothing to do             |
| Nodal-sum misfit gradient  | FEniCS: 78-line custom pyadjoint block    | Firedrake: 14 lines with a documented API     |
| Drag force                 | PICT: hand-written integration (L2)       | OpenFOAM: documented `forces` function object |

torch-fem shows the ladder moving as intended: its L3 monkeypatch was removed
in #187 when torch-fem 0.12.1 fixed device handling upstream.

**Asking "why" found real problems.** Independent of the ladder, the exercise
surfaced:

- dead code: Warp-NS `adjoint-grad-clip-3d` (unused since the lid-cavity mode
  was removed);
- unnecessary interventions: TopOpt.jl reads an undocumented struct field that
  the documented path already provides; the FEniCS structural L3 patch has no
  evidence of being needed on the cantilever;
- dormant code: OpenFOAM's Courant sub-stepping never triggers in any setup;
- comments whose stated reason looks wrong: the Warp-NS 3D eigenvalue
  "exact inverse", and the XLB channel staying on BGK because KBC drag is
  "non-smooth" (#194 measured smooth KBC drag gradients);
- upstream bugs worked around with no upstream issue: TopOpt.jl's INP parser,
  PhiFlow's warm-start tracer leak, PICT's orthogonal-scheme breakdown, XLB's
  packaging;
- a latent bug: the structural JAX-FEM setup cache is keyed on `pts.shape`,
  not the coordinates.

## Where the ladder does not fit

### 1. The level records the mechanism, not necessity or impact

Levels follow _how_ something was done, which conflates very different cases:

- A documented knob tuned by trial and error over three PRs (PhiFlow's CG
  tolerance) is L0; a one-line read of an undocumented field that changes
  nothing (TopOpt.jl) is L1.
- XLB ships halfway bounce-back, Zou–He, extrapolation outflow and a
  momentum-transfer operator, yet the tesseract hand-writes all of them
  (119 lines, L2) with no recorded reason. L2 by choice reads the same as L2
  by necessity.
- PICT's warm start is L3 only because of a private call in a VJP branch that
  no running experiment exercises. The forward branch that matters passes
  `x=` to a public function.

**Suggestion:** keep the level as the mechanism, and add a separate
`necessity` field (`required`, `choice`, `unknown`), plus a `tuned` flag for
values found by measurement.

### 2. Deviations from the setup are invisible

The ladder measures effort, not whether the solver solves the prescribed
problem:

- PICT has no pressure outlet and uses its own advective outflow. That is L0
  (documented, as in its samples), but it is a different boundary condition
  from the prescribed p = 0.
- OpenFOAM's graded channel mesh has a smallest cell of about 0.35 dx, so
  "10 cells per diameter" means different things for OpenFOAM and PICT.
- In harness code, TopOpt.jl gets the load as total force split evenly over
  the face nodes, because its INP format only takes normal pressure. The
  other solvers get a consistent traction.
- The harness gives only XLB a scaled time step and more steps on some
  ns-3d-grid experiments.

For a practitioner these deviations matter more than effort.

**Suggestion:** record them separately as _setup deviations_ (what differs
from the prescribed setup, and why), shown next to the checks.

### 3. The baseline depends on the library's abstraction level

- deal.II has no PDE-level API, so every user writes the assembly loop. The
  reviewer treated it as baseline, like writing UFL for FEniCS. Read strictly,
  it would be L2, like Warp-NS.
- Warp-NS is one L2 record covering about 2,500 of 2,800 lines, which makes
  the level uninformative. The benchmark-motivated numerics inside it (for
  example eigenvalues chosen to remove an FD-check bias) and the performance
  tuning advised by a Warp developer (NVIDIA/warp#1636) disappear into it.
- For XLB on JAX, it is unclear which library is "the solver": `jax.checkpoint`
  is documented JAX but not an XLB feature.

**Suggestion:** declare each solver's abstraction level (application,
framework, kernel toolkit) and define the baseline relative to it. Inside a
hand-written solver, record only interventions that answer to the benchmark,
not the solver itself.

### 4. Not every change is an intervention

Counting the following penalizes correctness and honesty, and should not be
recorded as interventions:

- fixes to Mosaic's own glue: removing redundant forward solves (#182, #229),
  INS.jl's ghost-cell refresh, arguably the nodal-misfit blocks;
- failure detection that changes nothing the solver computes (PICT's linear
  solve check, #226);
- converging an error control to a value where it no longer dominates
  (OpenFOAM momentum tolerance, #222; PhiFlow CG tolerance).

A further group adapts solvers to Mosaic's runtime rather than to the
problem: setup caches that restore "build once, solve many" under stateless
Tesseract calls (JAX-FEM, TopOpt.jl, FEniCS, Firedrake), Firedrake's TSFC
warm-up tuned to the single warm-up call of the timing protocol, and deal.II
launched as a subprocess per request. These change the cost results and are
applied unevenly; torch-fem has no setup cache.

**Suggestion:** treat runtime adaptation as a harness policy applied to all
solvers alike, not as per-solver interventions.

### 5. The rule on method artefacts is applied inconsistently

The spike found several likely conflicts with rule 3 (no workarounds for
artefacts of the method):

- XLB's smooth KBC stabiliser (L3, method change, verified in #194) removes
  the unbounded derivative of KBC's published formula. The switch from BGK to
  KBC above ω = 1.8 has no measurement behind its threshold.
- jax-cfd switched to central advection with RK4 to remove the O(dt) error of
  its default scheme (#225), while PICT's comparable PISO splitting error was
  deliberately kept as an explained anomaly.
- PhiFlow uses differential advection to avoid semi-Lagrangian gradient bias,
  but stays on explicit Euler although PhiFlow ships RK4.
- Exponax turns off its default dealiasing "to match other solvers". An
  Exponax run at N = 64 is also the reference for the ns-3d-grid forward
  checks, so this affects every solver's result.

Rule 4 (a method change creates a separate entry) is also not followed: XLB's
periodic results mix BGK and the modified KBC under one name.

These need a decision case by case. Choosing a non-default scheme that the
library ships is not covered by the current rules.

### 6. Rules 1, 2 and 5 cannot always be met

- PICT has no releases or tags; a commit pin is the only option.
- Legacy dolfin-adjoint will never release the fix the FEniCS L3 patch works
  around.
- Almost no workaround links an upstream issue.
- Applied strictly, rule 5 would remove interventions that are obviously
  necessary (for example L2 code that expresses the setup), because nobody
  wrote down the evidence.

**Suggestion:** allow "upstream unmaintained" and "no release process" as
recorded exceptions. Apply rule 5 with graduated evidence: `cannot-express` is
usually evident from the code; `too-slow` and `inaccurate-forward` need a
measurement; an inferred "why" opens an issue to measure it.

### 7. Gaps in the record format

- Missing consequences: non-reproducible results (torch-fem deterministic
  kernels, which also worsened a headline metric by removing a lucky escape
  from a plateau), optimizer stalls from a noisy loss, comparability with
  peers, consistency with the harness, and "no reason to be tighter".
- Some interventions have several consequences (PhiFlow's `XLA_FLAGS`: OOM and
  a crash).
- The root cause and what a user would observe can differ: the nodal misfit
  is `cannot-express` at the root but showed up as `incorrect-gradient`.
- The "why" depends on the setup, not the code region: the FEniCS MUMPS
  setting is identical in both tesseracts, but the out-of-memory evidence
  exists only for the heat slab.
- No way to mark inactive or dormant interventions, or code paths that never
  run.
- Provenance needs "maintainer-authored" (J. S. Dokken's FEniCS changes, the
  INS.jl author's Float32 fix) and "maintainer-advised" (the Warp developer's
  advice).

### 8. Line counts are a weak metric

- Code style dominates: the same tape-replay intervention is 71 lines in
  FEniCS and 13 in Firedrake.
- OpenFOAM's choices are single tokens inside dictionary templates written as
  Python strings, so markers can only wrap the whole template, and three ids
  share one region.
- Markers interact with tooling: isort splits import blocks at markers, and
  ruff format inserts blank lines before end markers.

Counting records per level and necessity is likely more informative than
lines per level.

### 9. Harness-side code

- `mosaic_shared/problems/navier_stokes_grid/ns_solver.jl` is INS.jl's solver,
  not harness code, and should probably live in the tesseract directory. As
  is, INS.jl shows zero intervention lines.
- `channel.py`'s `solid_cells` (the staircase cylinder) is part of the setup
  definition, but for PhiFlow it replaces the library's native obstacle.
- `grid_fluid.py` is not imported anywhere.
- The XLB time-step scaling and the TopOpt.jl load split live in the harness
  and cannot carry markers.

## Recommendation

Keep the ladder as one axis, and change the record around it:

1. **Level** stays the mechanism (L0–L3).
2. Add **necessity** (`required`, `choice`, `unknown`) and a **tuned** flag.
3. Split the record into **interventions**, **setup deviations** and
   **harness adaptations**. Bug fixes to Mosaic's own code and error controls
   are not recorded.
4. Declare each solver's **abstraction level** and define the baseline
   relative to it.
5. Make the "why" **per setup**, allow several consequences, and separate root
   cause from observed symptom. Extend the consequence and provenance
   vocabularies as listed above.
6. Decide the **method-artefact** cases in section 5, and either split XLB's
   periodic entry or document the mix.
7. Drop line counts per level as a headline metric.

## Cleanup independent of the ladder

Found along the way, worth fixing on their own:

- the JAX-FEM structural setup cache key (`pts.shape` instead of coordinates);
- Warp-NS dead code (`adjoint-grad-clip-3d`) and the doubtful 3D eigenvalue
  comment;
- firedrake-heat computes the misfit in float32 but builds its gradient seed
  in float64;
- `grid_fluid.py` appears unused;
- config comments that call jax-cfd "2D-only" and Exponax "3D-only", although
  both tesseracts implement both dimensions;
- missing upstream issues for the workarounds listed under "What works".
